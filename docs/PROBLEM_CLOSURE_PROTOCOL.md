# 需求落地闭环协议（Problem Closure Protocol）

> **用户裁定 2026-08-24 固化**："内容提出后需要落地，闭环"；"你负责整个流程的兜底，
> 要保证正确性"。本协议对所有会话（人工/cron）生效，是处理任何新需求/问题报告的
> 强制工作方式。

## 核心原则

1. **对话记忆不是记忆**。对话会被压缩、跨会话丢失。用户口头提出的每个需求，
   必须在本次会话内落到以下至少一层，否则视为未完成：
   - **配置**（instruments.json / x-influencers.json 等——配置即文档）
   - **代码**（脚本/管线行为）
   - **断言测试**（pytest / node 测试——让"提过"变成"测得到"）
   - **文档**（OPERATIONS_RUNBOOK / docs/uat 台账 / AGENTS.md）
2. **修复必须带回归用例**。任何 bug 修复，若无对应测试锁定，同一事故必然复发。
   历史证据：sync_layout 插入 bug 修了两次才加测试；来源窗口污染修了参数还要补
   filter_window 纵深防御。
3. **测试通过 ≠ 数据正确**。测试只守护"已知契约"。每个新需求的本质是扩充契约，
   必须同步扩充断言；只实现不断言的需求等于没做。
4. **兜底是流程的一部分**。校验失败时优先自动恢复（如晨报过期自动 force 补跑），
   而不是停下来等用户接管；无法自动恢复时必须显式标注缺口，禁止静默跳过。
5. **留痕对账**。一切降级/缺口/重试写入 evidence/cron-runs.jsonl 与 coverage；
   定期（每轮审计）回读台账核对承诺与产出的差值。
6. **不做超出用户要求的事（用户裁定 2026-08-26 持久化）**。用户指出问题后，
   默认只做两件事：①把问题对应的规则/口径修复并持久化到协议文档；②在后续流程中
   按新规则执行。**未经用户明确要求，不擅自修改已经发布的单份报告/数据层/历史产物**——
   即使修改看起来是"顺势而为"。单 case 的返工必须经用户开口。凡是规则的变更
   都要落盘；凡是落盘后能防止复发的事才做。

## 需求落地 Checklist（每个新需求逐项打勾）

```
[ ] 1. 需求落盘：写进配置/文档（含日期与用户裁定原话要点）
[ ] 2. 实现修改：代码或数据
[ ] 3. 断言守护：为该需求新增至少一条自动化测试（先想清楚"什么情况算坏了"）
[ ] 4. 纵深防御：问一句"如果上游再出错，这道防线拦得住吗？"（参照 filter_window 模式：
       入口修完后，出口再设一道硬校验）
[ ] 5. 全量验证：pytest 全绿 + node layout PASS + dist 字节一致
[ ] 6. 发布验证：push → Pages 部署 success → curl 线上抽查实际内容（非仅 200）
[ ] 7. 留痕：cron-runs.jsonl / UAT 台账 / runbook 步骤同步更新
[ ] 8. 回读复查：改动是否会破坏历史产物？（历史报告/归档需按新规则重生成吗？）
```

## 事故模式库（三轮审计沉淀，遇到同类症状直接套对策）

### 模式 A：结构合法但内容缺失
- **案例**：金龙组 `stocks: []` 长期无成分股但全部测试通过；晨报周一不生成导致融合页
  带旧数据上线；雪球缺口标记文件被 daily_scrum 判 [OK]。
- **症状**：所有断言绿色，但用户看到的内容缺了一块或方向不对。
- **对策**：内容完整性断言（stocks 非空、清单锁定）；新鲜度检查 + 自动兜底；
  缺口文件 [WARN] 显式化。**口诀：存在性检查之后，永远追问"内容对不对、新鲜不新鲜"。**

### 模式 B：字符串定位 / 默认值陷阱
- **案例**：`sync_layout` rfind 全文最后一个 "]);" 把条目插进 Promise.race 数组；
  `argparse append` 的 default 通配符永不消失导致跨窗口污染；`ROOT.glob` 不支持绝对路径。
- **症状**：修改"看起来生效"但在特定输入组合下静默错位/污染。
- **对策**：插入/替换点用结构化锚定（正则匹配目标块内部，而非全文 find）；
  可变默认值/追加式参数一律显式替换；修完必配回归用例（含边界输入）。

### 模式 C：语义合并 / 跨概念拼接
- **案例**：特朗普霍尔木兹+冈拉克英伟达兜底合并成一条；朱雀商业航天+阿里云算力拼一个
  主题；08-19 报告储能+光模块并购、全球基金+县域消费残留合并。
- **症状**：两个不同主体/动作/对象的事件出现在同一条目或同主题。
- **对策**：契约允许单条主题（2026-08-19 用户裁定）；收录规则写入报告头；
  新报告生成后人工复查一次语义分组；规则变更后回查历史产物并按新规则重生成。

## 收录线（用户裁定 2026-08-26 恢复）

- **主榜收录线固定为 50 分**（第二层 12:00 前旧闻按 0.4 折扣后 40+ 进 OLD 层）；
  50-92 分的独立事件全部入列，禁止以 60/64 分为线做"头部精选"。
- 历史教训：08-19 主题重构时收录线从 50 分漂移到 60-64 分，主榜从 35 条缩到
  9 条（08-17=52 条 / 08-18=41 条），被用户指出后恢复。
- 收录线变更必须经用户确认并同步更新本协议；任何"选项收窄"都要自检是否
  改变交付口径。
- **发现收录线漂移时的正确动作（08-26 用户裁定）**：只修正规则（本协议）并
  在下一期按新规则执行；**不返工已发布的单期报告**。已发布的历史报告保持
  发布时口径，作为当时的记录。（例外：用户明确授权返工时除外——08-28 案例）
- **收录线机器断言（2026-08-28 固化，防再次漂移）**：gen_report 契约预检内置
  两条检查——①NEW 最低分 >55 且无 floor_exempt 说明 → 报"收录线漂移"；
  ②NEW 条数 <10 → 报"疑似候选遗漏"。50 分线从"协议文字"变为"机器拦截"，
  与分数/主题契约同等强制。
- **other_news 明细化（2026-08-28 固化）**：50 分以下未入主榜事件必须逐条
  列出（标题+分数+说明+来源），禁止用"（阈值以下未单独入榜）"一句带过——
  用户有权知道"其他在哪里"。

## 定期审计机制

每轮审计固定动作（历史记录 → 配置 → 测试 → 线上四层对账）：

1. 回读 `evidence/cron-runs.jsonl` 与 `data/next-day-leads/`：有无漏跑/未消费承诺。
2. 对照本文档模式库逐项扫描新增代码/配置。
3. 抽查线上页面实际内容（curl 抓正文，不只看状态码）。
4. 发现问题 → 按 Checklist 走完整闭环 → 结果记入 `docs/uat/` 台账。
