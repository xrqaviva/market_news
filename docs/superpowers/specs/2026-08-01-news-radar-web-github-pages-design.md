# A股新闻雷达静态网页与GitHub Pages设计

## 1. 目标与成功标准

将项目中的Markdown新闻报告转换为视觉固定、信息紧凑、可公开访问的静态网页，并允许读者在不同日期、盘前、午间和盘后报告之间切换。

成功标准：

- Markdown始终是唯一内容源；不手工编辑结果HTML。
- HTML模板、CSS、JavaScript和转换器固定在`market_news`仓库中并接受测试保护。
- 每份Markdown生成一个具有稳定URL的独立HTML结果页。
- 左侧报告档案可以切换不同日期和时段；移动端使用折叠后的日期/时段选择器。
- 每日自动任务先生成Markdown，验证通过后再生成HTML并发布。
- 公网版本由GitHub Pages提供，不需要VPS或常驻后端。
- 发布失败时保留上一版可用网站，不以空页面或半成品覆盖。
- 公开仓库不包含证据文件、运行记录、浏览器数据、本机路径、凭据或本地配置。

## 2. 已确认的产品选择

### 2.1 视觉布局

采用用户选择并确认的B方案“研究终端”：

- 顶部深色状态栏展示当前报告、截点和统一北京时间口径。
- 桌面端左侧为报告档案和主题筛选，右侧为高密度新闻主榜。
- 新闻默认显示排名、标题、核心摘要、主要时间节点、热度权重和市场反馈标签。
- 点击新闻后在原位置展开关键信号、财报后反馈、判断边界、后续变量和具体来源链接。
- 移动端隐藏固定侧栏，改用顶部日期/时段选择器；内容保持单列。
- 模板视觉不随日报变化，日报只替换报告内容。

### 2.2 更新方式

采用自动同步：08:00任务生成Markdown后，继续执行固定转换器和网站发布流程。转换器和模板同时提供手动重建入口，便于补历史报告和故障恢复，但日常不依赖手工操作。

### 2.3 公网托管

采用GitHub Pages和双仓库方案：

- 当前`market_news`仓库保存Markdown、模板、转换器、测试和私有证据。
- 独立公开仓库`market-news-site`只接收构建目录中的公开静态产物。
- GitHub Pages从`market-news-site`发布公网网站。
- 公开网站无需服务器端代码、数据库或VPS。

## 3. 仓库结构

`market_news`新增以下固定结构：

```text
web/
├── templates/
│   └── report.html
├── assets/
│   ├── app.css
│   └── app.js
├── build.py
└── dist/
    ├── index.html
    ├── reports.json
    ├── assets/
    └── reports/
        ├── 2026-07-30-0800.html
        ├── 2026-07-30-1500.html
        └── 2026-07-31-0800.html
```

职责边界：

- `report.html`只定义稳定的页面语义结构和插槽。
- `app.css`只负责固定视觉系统、响应式布局和打印样式。
- `app.js`只负责报告切换、主题筛选、详情展开和移动端交互，不获取私有数据。
- `build.py`扫描合格Markdown，解析报告元数据和新闻条目，生成结果页、索引和最新报告入口。
- `dist/`是唯一允许同步到公开仓库的目录。

## 4. 内容模型与解析规则

### 4.1 报告元数据

转换器从文件名和报告正文提取：

- 报告日期；
- 时段标识，例如`0800`、`1200`、`1500`；
- 时段名称，例如盘前、午间、盘后；
- 新闻窗口起止时间；
- 实际采集截点；
- 合格新闻数量；
- 报告源Markdown路径。

新报告采用标准文件名`<YYYY-MM-DD>-<HHMM>-<name>.md`。转换器优先读取标准文件名，再以报告标题和窗口字段交叉验证；两者冲突或正文缺少关键窗口字段时，构建失败并明确指出文件，不进行发布。

历史文件采用固定兼容清单，避免把测试草稿和同日旧版本重复发布。首批公开历史报告为：

- `reports/2026-07-29-pure-news-hot-ranking-v4.md`；
- `reports/2026-07-30-premarket-news-ranking-v6-depth-test.md`；
- `reports/2026-07-30-1500-next-trading-day-news-baseline.md`；
- `reports/2026-07-31-0800-premarket-news-ranking.md`。

兼容清单显式给出每份历史报告的日期与时段；未来标准命名的日报自动进入索引，不需要继续维护清单。

### 4.2 新闻条目

每条新闻至少包含：

- 排名；
- 纯新闻标题；
- 核心信息；
- 热点权重及分项；
- 已取得的北京时间；
- 传播渠道和具体可点击链接；
- 热度变化。

Top 10额外解析：

- 关键信号或预期差；
- 财报后盘后、首个可交易时段或发布日余下交易时段反馈；
- 即时市场定价方向；
- 判断边界；
- 后续变量。

第11名以后保持紧凑；页面不根据字段缺失补造结论。可选字段不存在时不显示对应模块，但最低必需字段缺失会阻断该报告发布。

### 4.3 独立结果页

每份Markdown生成一个独立结果HTML：

```text
reports/<YYYY-MM-DD>-<slot>.html
```

规则：

- 相同报告重复构建时覆盖对应HTML，URL保持不变。
- 新报告新增一个结果页，并更新`reports.json`。
- `index.html`进入`reports.json`中最新的有效报告。
- 报告索引按日期降序，同日按盘后、午间、盘前的时刻降序展示。
- 历史结果页能够直接收藏和分享。

## 5. 页面交互

### 5.1 报告切换

- 左侧档案按日期分组，展示时段、合格新闻数和当前选中状态。
- 点击档案进入对应独立HTML页面，而不是在浏览器中解析Markdown。
- 移动端以选择器替代侧栏，选择后进入对应结果页。
- `reports.json`提供统一索引，因此新增报告不要求修改固定模板代码。

### 5.2 新闻阅读

- 主榜默认高密度单列，排序完全沿用Markdown报告。
- 点击条目只展开当前新闻的深度字段，再次点击收起。
- 具体来源在展开区按北京时间从早到晚排列，并直接链接到原始文章、公告或帖子。
- 正向、负向、分化和不可得使用不同颜色，但颜色只表示报告已有标签，不形成买卖建议。
- 热度变化、激增和新出现只显示在详情，不进入标题。

### 5.3 筛选与可访问性

- 主题筛选仅改变当前页面显示，不改变排序和报告数据。
- 所有交互支持键盘操作、清晰焦点状态和语义化按钮。
- 正文颜色满足可读对比度，不能只依靠红绿颜色传达含义。
- 移动端不横向滚动，外链和长标题允许自然换行。

## 6. 构建与自动发布

自动流程：

```text
08:00任务生成Markdown
        ↓
Markdown完整性验证
        ↓
固定转换器生成独立HTML、索引和静态资源
        ↓
HTML结构、公开范围和浏览器验收
        ↓
同步web/dist/到market-news-site
        ↓
Git提交与推送
        ↓
GitHub Pages发布
```

发布约束：

- 构建和验收全部通过后才允许同步公开仓库。
- 同步采用“完整构建目录替换公开产物”的方式，避免历史残留，但必须先验证目标目录是预期的`market-news-site`工作区。
- 不使用宽泛或未解析路径执行删除、覆盖或推送。
- GitHub认证使用本机已有SSH或安全凭据；凭据不得写入仓库、HTML、日志或自动任务提示词。
- 自动发布需在用户授权创建公开仓库并首次推送后启用。
- 08:00自动任务保持单次主流程：Markdown成功后调用构建和发布脚本；中午和盘后自动任务继续保持暂停，除非用户另行启用。

## 7. 失败处理

### 7.1 Markdown失败

- Markdown未生成或未通过原报告验收时，不执行网页构建和发布。
- 保留上一份成功生成的Markdown及公网页面。
- 自动任务记录明确失败原因。

### 7.2 转换失败

- 任何报告出现无法解析的必需字段时，构建命令非零退出。
- 在临时构建目录完成全部生成和验证，成功后才替换`web/dist/`。
- 不产生部分更新的公开目录。

### 7.3 发布失败

- Git同步、提交、推送或GitHub Pages发布失败时，保留本地成功生成的Markdown和HTML。
- 不回滚或删除上一版公网页面。
- 自动任务将发布失败与新闻报告失败分开记录。
- 下次运行可重新发布相同结果，不生成重复报告URL。

## 8. 安全与公开边界

公开内容仅包括：

- 新闻报告正文；
- 报告元数据；
- 原报告中已经公开的具体来源链接；
- 固定HTML、CSS、JavaScript和必要的公开索引。

不得公开：

- `evidence/`；
- `findings.md`、`progress.md`、`task_plan.md`和`HANDOFF.md`；
- `.superpowers/`、`.planning/`、浏览器快照和本地调试文件；
- Cookie、密码、Token、Local Storage、浏览器历史或登录会话信息；
- `/Users/...`等本机绝对路径；
- Git认证配置、SSH密钥和环境变量。

构建后必须扫描`web/dist/`，发现以上内容或敏感模式时阻断发布。

## 9. 测试与验收

### 9.1 单元测试

- 文件名与时段解析；
- 报告元数据解析；
- Top 10与紧凑条目解析；
- 时间、热点权重、市场反馈和来源链接解析；
- 缺失必需字段时构建失败；
- 相同报告重复生成保持相同URL。

### 9.2 集成测试

- 多份历史Markdown一次构建生成多个独立HTML和正确的`reports.json`；
- `index.html`进入最新有效报告；
- 新增报告后旧页面URL仍存在；
- 模板、资源和结果页引用路径在GitHub Pages项目子路径下有效；
- 构建失败不替换上一版`dist/`。

### 9.3 模板稳定性测试

- 对固定模板结构建立快照或结构契约，日报内容变化不能改变导航、主榜、详情和来源区域的语义层级。
- 模板变更必须显式更新测试，不能由Markdown内容意外驱动。

### 9.4 浏览器测试

- 桌面端验证左侧报告切换、筛选、详情展开、外链和最新报告入口。
- 移动端验证日期/时段选择器、单列布局、长标题和无横向滚动。
- 检查浏览器运行时无JavaScript错误和资源404。

### 9.5 发布范围测试

- `web/dist/`不得出现本机绝对路径、凭据模式或私有文件名。
- 公开仓库同步前复核实际文件清单和内容，不只检查文件名。
- GitHub Pages地址返回成功，最新报告和至少一个历史报告可访问。

## 10. 替代方案与取舍

### 单仓库GitHub Pages

优点是配置最少；缺点是免费方案通常需要公开源仓库，会把证据、运行记录和项目内部文件暴露风险扩大，因此不采用。

### Cloudflare Pages

支持私有仓库和静态托管，能力充分；用户明确选择GitHub，因此不采用。

### 本地HTML

无需发布配置，但无法满足公网访问，因此仅保留为构建后的本地预览方式。

### 动态网站与数据库

可以提供服务端搜索和权限控制，但增加部署、维护和安全成本；当前报告规模使用静态页面已经满足需求，因此不采用。

## 11. 实施边界与授权

本设计授权范围只包括在当前项目中准备模板、转换器、测试和静态产物。以下外部变更必须在实施阶段获得明确授权并完成只读确认：

- 创建GitHub公开仓库`market-news-site`；
- 首次推送和启用GitHub Pages；
- 修改08:00自动任务以调用构建及发布；
- 后续任何自定义域名、访问统计、认证或付费服务。

中午12:00和下午15:00自动任务保持暂停，不属于本次启用范围。

## 12. 最终验收

交付完成需同时满足：

- 固定模板和转换器已纳入当前Git仓库；
- 所有现有合格Markdown均能生成独立HTML；
- 不同日期和时段可在页面切换；
- B方案视觉在桌面和移动端通过浏览器验收；
- Markdown失败、转换失败和发布失败均不会覆盖上一版网站；
- 公开目录敏感信息扫描通过；
- 独立只读审阅无阻断项；
- 用户授权后，GitHub Pages公网地址可以访问最新报告和历史报告；
- 未启用午间和盘后自动任务。
